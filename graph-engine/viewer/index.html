A CSPM tells you a role can read the PII store. It cannot tell you whether it ever has — that requires a second, independently-collected fact: access telemetry, joined against the declared grant. i-checkout-api-1 and i-checkout-api-2 are identical twins — same role, same declared reach — but only one of them has ever actually touched the store. Declared access with no matching observed access, inside a trust window, is the finding. That cross-reference is exactly what edge aliases and a correlated NOT EXISTS were added to this DSL for.

Goal — why a graph engine, not a report

Standard CSPM tooling answers what a role can do, from the declared IAM policy. It has no way to say whether that access was ever exercised — that needs a second, independently-collected signal (access telemetry) joined against the declared grant, per workload, per action, inside a trust window.

That join is naturally a graph problem: two paths through the same inventory — declared (Workload → RUNS_AS → IAMRole → CAN_READ → DataStore) and observed (Workload → ACCESSED → DataStore) — that have to be correlated node-by-node and edge-property-by-edge-property. A relational join across two tables could express this too, but it wouldn't compose with the rest of the inventory already modeled as one graph (cost, exposure, blast radius). The point of building this here is that "unused, and internet-facing, and reaches PII" becomes one more WHERE clause on the existing graph, not a new pipeline.

Why this needed a DSL extension

v1 had no way to bind the specific CAN_READ edge traversed ([g:CAN_READ]), no way to compare one alias's property against another's (a.action = g.action), and no way to ask a graph "does this not exist" at all. Computing this finding used to mean exporting both edge sets and diffing them downstream. Now it's one query, run in-engine, streamed like any other.

API Cypher-inspired DSL

MATCH / WHERE / RETURN mirrors openCypher on purpose — capitalizing on existing knowledge rather than inventing a new syntax nobody has seen before. Anyone who has written a Neo4j query already knows how to read one here.

It is a deliberately small subset, extended in-house only when a concrete use case needed it: edge aliases ([g:CAN_READ]), RETURN alias.property, cross-alias property comparison (a.action = g.action), and a correlated NOT EXISTS — the last three added for the Unused permissions tab specifically, not speculatively.

Storage Apache Iceberg

Every node/edge label is its own Iceberg table (node_<Label>, edge_<TYPE>) in a shared catalog + warehouse. Iceberg gives snapshot isolation and schema evolution without the engine having to implement either.

The read/write split is strict: a separate batch pipeline (ingest-*) writes snapshots; the query engine only ever reads a pinned snapshot and rebuilds its in-memory index from it on a timer. There is no write path inside the serving engine.

Index B-Tree + CSR, no aggregation index

  • B-Tree (property index): equality/range lookups on @indexed properties, per partition. Resolves a query's anchor — e.g. finding the Resource node with name = "i-checkout-api-1".
  • CSR / topological index (graph index): a compressed adjacency list per partition, used for navigation. A k-hop traversal walks it directly.
  • Pattern matching reuses the same CSR index: a MATCH pattern compiles to a chain of hops over the topological index — there is no separate "pattern index"; a pattern is just hops with extra WHERE filters attached.

No dedicated aggregation index yet — there is no COUNT/SUM in the DSL at all (explicit non-goal for now). Adding one is future work if a real use case demands it.

Engine Distributed, for horizontal scale

Two binaries: graph-coordinator (stateless — plans a query, then scatter-gathers it) and graph-partition-node (owns one hash-partition's index generation, rebuilt periodically from Iceberg with an atomic swap so readers never see a half-built index).

A query's start is broadcast to every partition (the property index is local, not global), then each hop groups the current frontier by owning partition and fans out one RPC round per hop.

Cross-partition graph traversal is the hard part: an edge whose destination lives on another partition is carried forward as a remote reference and re-routed into the next network round instead of resolved locally — more hops means more round trips, and a NOT EXISTS anti-join needs its own RPC per (partition, group) rather than reusing a plain hop. Verified against a real two-partition cluster, not simulated in a single process.
